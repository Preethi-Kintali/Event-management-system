2. Project Summary

2.1 Purpose of the Project

Eventura Platform (branded as Eventura) is an enterprise-grade, multi-tenant Event, Competition, Hackathon, and Innovation Management Platform engineered for higher educational institutions, collegiate consortiums, technology communities, and corporate hackathons. The primary purpose of Eventura is to eliminate the severe fragmentation of conventional event organization—which relies on disjointed Google Forms, WhatsApp groups, manual judging spreadsheets, paper budget approval requests, and non-verifiable paper certificates—by unifying all operational stages into a single, cohesive, role-governed digital operating system.

2.2 Business Problem It Solves

  • Approval Bottlenecks: Paper proposal forms delayed for weeks across department offices.
  • Roster Chaos: Uncontrolled member swaps and duplicate registrations on demo day.
  • Biased & Delayed Judging: Manual paper scoring leading to tabulation delays and errors.
  • Gate Congestion: Slow physical check-in lines causing bottleneck queues at venues.
  • Credential Forgery: Unverifiable paper certificates vulnerable to tampering.
  • Post-Event Reporting Friction: Weeks spent gathering stats for accreditation boards.

2.3 Intended Users

  • Institutional Admins & Principals: Formal event sanctions, venue allocation, governance.
  • Event Managers & Officers: Rubric design, track config, budget approvals.
  • Student / Faculty Coordinators: Proposal drafting, team tracking, AI dossier creation.
  • Evaluators & Judges: Real-time digital scorecards, qualitative reviews.
  • Volunteers: High-speed QR gate pass scanning with camera.
  • Hackers & Participants: Team formation, project delivery, verifiable credentials.
Current Operational Status: Production Handover & Active Staging Development
The core backend (Express + PostgreSQL + Prisma ORM) and frontend (React 19 + TanStack Router) are fully implemented, fortified with multi-tenant tenant isolation and RBAC. All functional workflows—including Stripe payment settlement, Google Gemini AI dossier synthesis, and offline-resilient QR gate check-ins—have passed automated smoke and multi-tenant stress tests.

3. Business Context

3.1 Why Was This Project Built?

Institutional hackathons and innovation symposiums have transitioned from informal club activities into massive multi-stakeholder summits involving thousands of competitors, corporate sponsors, intellectual property submissions, and substantial institutional budgets. Despite this growth, management methodologies remained obsolete. Universities frequently incurred audit penalties, delayed student awards, lost track of sponsor funds, and struggled to compile compliance dossiers for national accreditation bodies (such as NAAC, NBA, and ABET). Eventura was conceived to modernize collegiate event governance with the same rigor found in enterprise ERP systems.

4. System Overview

4.1 Application Description in Plain Terms

Eventura operates as a full-stack, multi-tenant Software-as-a-Service (SaaS) web application. Each university, college department, or company operates within its own strictly isolated organization realm (organizationId). When a user navigates to the platform, the client application executes role-based route matching. Behind the scenes, incoming requests pass through a multi-tier security perimeter that validates JWT authenticity, resolves active tenant membership, checks granular permissions (e.g., events.create, evaluations.manage), and applies tenant scoping at the repository level before interacting with PostgreSQL.

Dependencies: Event Service, Audit Logger, Notification Service.

Purpose: Manages specific hackathon problem statements and challenge domains.

Responsibilities: Rule definition, team size constraints (e.g. 2-5 members), prize allocation, and rubric linking.

Main Features: Multi-track events (AI, Web3, IoT), custom eligibility criteria, judging committee assignment.

5. Team Registration & Roster Lock

Purpose: Facilitates participant sign-up and prevents competition fraud.

Responsibilities: Invitation code generation, captain leadership transfer, member approval, and automated roster freeze.

Main Features: Automated locking at submission deadline, duplicate prevention, payment status binding.

Dependencies: Registration Repository, Stripe Payments.

6. Submission & Artifact Hub

Purpose: Collects and preserves competition deliverables.

Responsibilities: GitHub repository linking, demo pitch video URL, slide deck PDF storage, and immutable timestamping.

Main Features: Lockout upon timer expiration, file upload validation, version history tracking.

Dependencies: File Storage Service, Event Timer Service.

7. Rubric Evaluation & Scoring

Purpose: Eliminates subjective bias through structured digital scorecards.

Responsibilities: Weighted criteria evaluation, score normalization across judge panels, draft saving, and podium locking.

Main Features: Real-time leaderboard updates, blind evaluation modes, qualitative feedback logs.

Dependencies: Submission Repository, Judge Assignment Model.

8. QR Gate Attendance Scanner

Purpose: Accelerates physical check-ins during high-volume event mornings.

Responsibilities: Dynamic QR passport generation, camera scanner execution, offline scan caching, and double-entry prevention.

Main Features: Sub-second visual confirmation (Green/Red), session check-in logs, real-time turnout counter.

9. Tamper-Proof Digital Certificates

Purpose: Issues permanent, verifiable credentials to attendees and winners.

Responsibilities: Dynamic vector PDF synthesis, SHA-256 cryptographic serial hashing, and public verification routing.

Dependencies: PDFKit, QRCode Generator, Certificate Repository.

7.2 Detailed Step-by-Step Workflow Description

  1. Proposal Drafting (Student Coordinator): Coordinator drafts dates, target headcounts, itemized budget items, and required campus venues (e.g., Main Auditorium). Proposal is submitted with status DRAFT → PENDING_REVIEW.
  2. Manager Evaluation (Event Manager): Manager verifies budget feasibility, checks campus calendar for date collisions, and appends recommendations.
  3. Executive Sanction (Principal / Director): Highest authority clicks formal approval. System sets event status to APPROVED, locks venue reservation, and unlocks operational tracks.
  4. Track Configuration & Setup: Manager sets problem statements, team bounds (2-5 hackers), judging rubric criteria (Innovation 40%, Technical Depth 30%, Viability 30%), and registration windows.
  5. Team Registration & Ticketing: Hackers register, pay fees via Stripe (if ticketed), form teams with invite links. When deadline hits, team rosters freeze permanently.
  6. Gate Check-In: Volunteers scan attendees' encrypted QR passes via mobile phone cameras. Gate logs update in real time; proxy attendance is prevented.
  7. Hackathon Submissions & Freeze: Teams upload GitHub URLs, pitch decks, and live demo links. When the countdown hits 00:00:00, all submissions lock.
  8. Judging & Rubric Normalization: Judges evaluate assignments on mobile scorecards. Scores are automatically normalized across panels to prevent outlier bias.
  9. Leaderboard & Winner Declaration: Winners and podium standings are finalized. Cash prize allocations are recorded.
  10. Automated AI Dossier & Certificate Dispatch: Gemini AI synthesizes the comprehensive post-event dossier with institutional formatting. Dynamic vector PDF certificates with SHA-256 QR codes are dispatched to all participants.

13. Known Limitations

1. Concurrency Limits on Single Node

Under a single-process Node.js runtime, peak throughput is capped at ~2,500 requests/sec. For massive collegiate symposiums exceeding 5,000 simultaneous gate scans, horizontal clustering (PM2 / Kubernetes) and PgBouncer connection pooling must be enabled.

2. Database Connection Pool Ceiling

Prisma's default connection pool allocates 10 connections. High-burst traffic during morning attendance check-ins requires sizing the pool to match Postgres max_connections to avoid queue timeouts.

3. Local Filesystem File Uploads

The development configuration stores user uploads in the local uploads/ directory. For multi-instance cloud deployments, an S3 or Cloudflare R2 bucket driver must be configured to share uploaded files across nodes.

4. Real-Time Leaderboard Polling

The current leaderboard and check-in metrics operate via TanStack Query optimistic updates and polling intervals (5-15 seconds). Future releases plan native WebSocket integration for sub-second leaderboard broadcasts.

14. Maintenance Notes

14.1 Operational Procedures & Scheduled Jobs

  • Nightly Registration Expiration Job: Cleans up unconfirmed or unpaid registration drafts after the designated 48-hour reservation window expires.
  • Database Backup Strategy: Daily automated full pg_dump snapshots with Continuous WAL Archiving (Point-in-Time Recovery enabled for up to 30 days).
  • Log Aggregation & Monitoring: Application events emit structured JSON to stdout containing timestamp, HTTP method, route, response status, and duration (ms). Critical exceptions trigger alert notifications.

14.2 Troubleshooting Quick Reference

Symptom Probable Cause Remediation Step
Connection Refused (5432) PostgreSQL service stopped or stale postmaster.pid. Verify service via pg_ctl status, remove stale pid file if ungracefully stopped, and restart.
401 Unauthorized Errors Expired JWT token or missing authorization header. User session expired. Client will automatically trigger refresh token endpoint or prompt clean login.
Stripe Webhook Mismatch Missing raw body buffer or invalid STRIPE_WEBHOOK_SECRET. Ensure webhook route is registered BEFORE express.json() parser with express.raw().
Vite CORS Errors Frontend URL port differs from allowed origins in app.ts. Add the active client port (e.g., http://localhost:8080) to the allowedOrigins array.
